# RFID Jukebox (Embedded Systems Project)

The RFID Jukebox is an embedded music playback system inspired by the Minecraft jukebox mechanic. Inserting an RFID-tagged “disc” triggers playback of a corresponding song, mimicking the in-game experience using real hardware.

The project began as a Raspberry Pi–based prototype to simplify development and debugging, then evolved into a fully embedded Arduino-based system to improve efficiency, boot time, and power usage. This transition forced a fundamental redesign of both the electrical architecture and software stack, deepening my understanding of microcomputers vs microcontrollers.

## Features

Here's what you can do:

- Detect physical input via RFID.<br>
- Map unique RFID UIDs to audio files.<br>
- Play audio reliably with minimal latency.<br>
- Design a system that could transition from prototyping to a permanent embedded solution.

## 👩🏽‍🍳 The Process

There are a lot of parts on this Jukebox project, including Arduinos, 3D modeling, and 3D printing. However, I will only go over the electrical architecture.

### 🍓 Raspberry Pi–Based Architecture

At the core of the first version was a Raspberry Pi 4, acting as a full Linux computer responsible for:<br>
- RFID communication<br>
- Audio playback<br>
- Input handling<br>
- File management<br>
This approach prioritized development speed and visibility over efficiency. The RC522 RFID module communicates using the SPI protocol, with the Raspberry Pi acting as the SPI master.

Key design decisions:<br>
- SPI was chosen for its speed and reliability<br>
- The RC522 was powered at 3.3V to avoid hardware damage<br>
- Hardware SPI pins were used to ensure proper timing<br>

SPI Signal Roles<br>
- **SCK:** Clock generated by the Pi<br>
- **MOSI:** Commands sent to the RC522<br>
- **MISO:** UID data returned by the RC522<br>
- **CE (SDA):** Chip select to activate the RFID reader<br>
- **RST:** Software-controlled reset<br>
Rather than using interrupts, the system polled for RFID tags, simplifying control flow and avoiding race conditions during early development.

The Pi runs Raspberry Pi OS (Linux), which allowed rapid iteration and debugging.

Key libraries:<br>
- **mfrc522** → RFID communication over SPI<br>
- **RPi.GPIO** → GPIO handling<br>
- **pygame.mixer** → MP3 audio playback

Program Logic<br>
- The program runs in a continuous loop<br>
- When a tag is detected, its UID is read via SPI<br>
- The UID is matched against a Python dictionary<br>
- Each UID maps directly to an MP3 file stored on the Pi<br>
- Audio playback is handled entirely in software<br>
This architecture made the system easy to extend: adding a new disc required only assigning a new UID and MP3 file.

### 🤖 Arduino-Based Architecture

The final design uses an Arduino Nano, shifting from a microcomputer to a real-time embedded system. This is because Arduinos:<br>
- Do not run an OS<br>
- Cannot decode audio in software<br>
- Have no filesystem<br>
…the architecture had to change significantly.

Modular Hardware Design:<br>
- **RC522 RFID Reader:** Fast, synchronous communication, managed directly by Arduino hardware, uses fixed pins (D10–D13) <br>
- **UART (Audio Module):** Serial communication via SoftwareSerial and sends simple commands like “play track 2” <br>
Managing two protocols simultaneously reinforced my understanding of timing, data flow, and resource constraints in embedded systems.

Communication Protocols<br>
- **SPI (RFID):** Handles disc detection and communicates via SPI <br>
- **RC522 RFID Reader:** Handles disc detection and communicates via SPI <br>

The Pi runs Raspberry Pi OS (Linux), which allowed rapid iteration and debugging.

Arduino Software Architecture:<br>
The Arduino version was written in C++, requiring:<br>
- Explicit memory management<br>
- Static data structures<br>
- Deterministic control flow

Libraries used:<br>
- MFRC522.h → RFID communication<br>
- DFRobotDFPlayerMini.h → Audio playback<br>
- SPI.h and SoftwareSerial.h

Program Flow<br>
1. Initialize SPI and RFID reader<br>
2. Initialize serial communication with DFPlayer<br>
3. Continuously scan for RFID tags<br>
4. Read and assemble UID bytes<br>
5. Match UID using conditional logic<br>
6. Trigger the corresponding MP3 track<br>
Unlike Python, where dictionaries made mapping easy, the Arduino version required manual UID comparisons due to memory limitations—highlighting the trade-offs of low-level systems.

Results of the Transition<br>
- Instant boot (no OS)<br>
- Lower power consumption<br>
- More reliable long-term operation<br>
- Cleaner separation between sensing and actuation<br>
This redesign transformed the jukebox from a prototype into a true embedded system.

## 🏢 Physical Architecture (Brief)<br>
The physical enclosure and disc mechanism were 3D modeled and printed to resemble the Minecraft jukebox. The design focused on:<br>
- Proper RFID alignment<br>
- Internal component clearance<br>
- Disc insertion and ejection<br>
While important for usability, the primary engineering challenge and learning focus of this project was electrical and embedded system design.
